# Checklist: 逻辑与算法需求质量验证

**Purpose**: 本清单作为“需求的单元测试”，专门验证《特性说明书 [spec.md](../spec.md)》中关于 PCG (程序化生成) 与难度梯度算法逻辑的完整性与严谨性。
**Target Audience**: 架构评审者 (PR Reviewer)
**Focus Areas**: 算法幂等性、可解性保障、混合模式逻辑

## 算法幂等性与种子逻辑 (Seed & Idempotency)

- [x] CHK001 - 是否明确规定了种子 (Seed) 的生成时机（如：进入关卡时生成 vs 用户安装后固定）？ [Clarity, Spec §FR-002]
- [x] CHK002 - 需求是否涵盖了“跨设备复现”的要求，即在相同平台下不同设备使用同一种子是否必须产出 100% 一致的布局？ [Gap, Ambiguity]
- [ ] CHK003 - 对于依赖物理引擎的游戏（如弹弹球），需求是否说明了如何处理因浮点数误差导致的“种子布局一致但运行轨迹发散”的情况？ [Edge Case, Gap]
- [x] CHK004 - 关卡生成所需的伪随机算法 (PRNG) 是否规定了具体的实现模型 (如 LCG 或 MT)？ [Clarity, Plan §Phase 2]

## 难度梯度与数学模型 (Difficulty Modeling)

- [x] CHK005 - 需求中提到的“线性梯度计算”是否明确了各游戏的不同权重系数（例如：动作类的重力增长系数 vs 益智类的路径复杂度系数）？ [Completeness, Spec §FR-001]
- [x] CHK006 - 对于“无尽模式”，是否定义了难度增长的阶梯触发条件（按时间、按分数、还是按移动距离）？ [Clarity, Spec §FR-004]
- [ ] CHK007 - 是否明确定义了难度因子的“饱和阈值”，即达到何种程度后不再进行物理参数的增强？ [Gap, Spec §边缘情况]
- [x] CHK008 - 需求是否规定了难度系数与随机生成算法之间的映射关系（如：难度 X 对应生成 Y 个障碍物）？ [Clarity, Spec §FR-003]

## 可解性与安全边界 (Playability & Safety)

- [x] CHK009 - “100% 确保可通关 (SC-001)”是否在需求中分解为各游戏的最小逻辑闭环校验？（如：Poly 必须存在非交叉路径） [Completeness, Spec §SC-001]
- [x] CHK010 - 是否定义了生成失败时的“兜底方案”（如：算法无法在 200ms 内生成合法关卡时，是否加载预设的 Back-up 布局）？ [Edge Case, Gap]
- [x] CHK011 - 算法需求中是否包含对“极端不利布局”的规避规则（如：涂鸦跳跃中连续出现不可调跳跃距离）？ [Consistency, Spec §SC-001]

## 存储与状态一致性 (Persistence & Consistency)

- [x] CHK012 - 里程碑存档需求是否明确了存储的具体数据结构（仅 Level 数，还是包含当前的随机种子）？ [Clarity, Spec §FR-005]
- [x] CHK013 - 是否规定了当用户在“中途强制退出”时，当前关卡的进度是视为失败重置还是保留当前种子？ [Consistency, Gap]
- [ ] CHK014 - 需求是否涵盖了“版本迁移”场景：当生成算法逻辑优化后，旧版本的存档数据如何映射到新算法的难度等级？ [Gap, Assumption]
