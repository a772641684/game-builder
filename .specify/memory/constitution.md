# 萌鱼泡泡 (Bubble Fish) 项目宪法

## 核心原则

### I. 命名与结构规范

代码库必须遵守严格定义的命名约定及目录结构，以确保代码的可预测性。

- **类/接口**：必须使用 大驼峰（PascalCase）。接口必须以 'I' 开头命名（例如 `IPerson`）。
- **函数/变量**：必须使用 小驼峰（camelCase）。
- **常量/枚举**：必须使用 大写字母加下划线命名（UPPER_CASE）。
- **禁用项**：普通变量或函数名中禁用下划线。
- **依据**：在大型 Cocos Creator 项目中，一致性对于可维护性至关重要。

### II. 静态分析与格式化

代码风格通过自动化工具强制执行，不应成为人工争议的焦点。

- **工具**：必须启用 ESLint（Alloy 配置）及 Prettier。
- **全等判定**：必须使用 `===` 及 `!==`。
- **变量声明**：必须使用 `const` 或 `let`。严禁使用 `var`。
- **箭头函数**：表达式必须使用箭头函数；`function` 关键字受到限制。
- **语法限制**：严禁使用 TypeScript 的 `??` (Nullish Coalescing) 语法，必须使用 `||` 或显式的空值检查代替，以确保在旧版引擎及压缩环境下的极端兼容性。 (P20)
- **依据**：减少语法的多样性可以降低认知负担，并防止常见的 JS/TS 陷阱。

### III. 类型安全与完整性

使用 TypeScript 来防止运行时错误；绕过类型系统属于违规行为。

- **禁止使用 `any`**：除非确实无法避免，否则严禁使用 `any` 类型。如果使用了，必须给出合理理由。
- **显式定义**：函数及变量应该有显式的类型定义，或者依赖清晰的类型推导。
- **不变性**：对于初始化后不应更改的属性，请使用 `readonly`。
- **依据**：类型安全确保了整个应用程序中数据结构的严谨性。

### IV. 框架防护（Loader 优先）

限制对引擎内部实例化及加载的直接访问，以防止资源泄漏。

- **实例化**：必须使用 `Loader.getInstance().instantiate` 代替 `cc.instantiate`。
- **资源加载**：必须使用 `Loader` 或 `RemoteImage` 类的对应接口代替直接调用 `cc.loader`。
- **依据**：中心化的资源管理对于高效的内存及资源处理是必要的。

### V. 日志与可观测性

标准输出预留给平台层；应用逻辑必须使用专门的日志记录器。

- **日志记录**：禁用 `console.log`。必须使用 `Logger.getInstance().log/warn/error`。
- **参数顺序规范**：调用日志记录器时，第一个参数必须是 **系统/模块/标签 (Tag)**，第二个参数必须是 **具体日志内容 (Message)**。例如：`Logger.getInstance().info("Game", "初始化完成")`。
- **内容语言**：日志中的描述消息字符串必须使用 **中文**，以便于团队快速定位及 AI 进行故障分析。
- **依据**：结构化日志有助于更好的过滤、远程调试以及环境感知输出。一致的参数顺序确保了日志组件的可读性与自动化处理能力。

### VI. 注释文档规范

代码注释与文档必须使用中文，以确保团队沟通的一致性及高效性。

- **强制注释**：新增的所有公共/私有方法、全局函数必须补全 JSDoc 格式注释，明确说明功能意图、参数含义及返回值。
- **语言要求**：所有后续新增的功能逻辑、复杂的算法说明、公共 API 的 JSDoc 注释、**日志打印内容 (Logger message)**、以及所有 Markdown (`.md`) 文档必须使用中文（关键技术术语除外）。
- **流程文档规范**：`spec.md` (需求说明)、`plan.md` (实施方案) 以及所有 `checklists/*.md` (质量自检清单) 必须全程使用中文编写，除专有名词外禁止使用英文。
- **自检清单规范**：所有 `checkList` 相关的 Markdown 文件及其模板必须强制使用中文，以确保 AI 能够准确理解质量评估标准。
- **Git 提交信息**：所有 Git commit message 必须使用中文（或约定式提交前缀: 中文描述格式，如 `feat: 新增道具系统`），以确保版本历史的可读性。
- **依据**：为了减少跨团队（以及与 AI 助手）理解代码时的文化与语言隔阂，提高自动化工具分析性能，并确保项目文档对所有成员（及 AI）具有最高的可理解性。

### VII. 动画与坐标变换

统一动画开发模式，确保多分辨率适配下的表现一致性。

- **Tween 优先**：必须使用 `cc.tween` 进行动画开发，严禁在业务逻辑中使用旧版的 `cc.Action` API。
- **跨空间坐标转换**：节点在不同父级间移动或同步位置时，必须使用 `convertToWorldSpaceAR` 配合 `convertToNodeSpaceAR`。
- **依据**：标准化坐标转换可避免因层级嵌套导致的位移偏差；`cc.tween` 更易于维护及链式表达。

### VIII. UI 与组件架构

明确 UI 面板与场景物体的职责边界。

- **脚本前缀规范**：
    - 挂载在 Prefab 实例上的组件脚本（如游戏内物体）必须以 `Prefab` 开头（如 `PrefabGameCarBus.ts`）。
    - 负责整个 UI 面板逻辑的控制器以功能命名（如 `UIPlayGroundGameCar.ts`），并位于 `assets/script/ui/`。
- **解耦通讯**：主控类使用 `public static instance` 模式，在 `onLoad` 初始化，在 `onDestroy` 销毁。
- **循环依赖限制**：挂载在 Prefab 上的脚本组件之间严禁形成循环引用。循环依赖会导致 Cocos Creator 2.x 的脚本注册机制失效，表现为 Class ID 匹配但组件仍显示 Invalid。必须通过事件总线（P12）或接口层进行解耦。
- **Prefab 结构与属性文档化**：对于继承自 `cc.Component` 的类，必须在脚本 JSDoc 中包含以下信息：
    - **类级别 [Prefab 结构说明]**：该说明是自动化工具（或 AI）生成及修复 Prefab 节点树的唯一权威依据。描述必须包含预制体根节点名、必选子节点名及其层级。
    - **成员级别 @property JSDoc**：若包含 `@property` 装饰的成员变量，必须详细描述其对应的节点路径及组件类型。
- **UI 资源规范**：小游戏的主预制体（Panel）必须放置在 `assets/resources/ui/` 目录下，并确保在 `assets/script/enums/UIEnum.ts` 的 `UI_ENUM` 常量中同步配置，以便通过 `UI.getInstance().open()` 进行动态加载。 (P19)
- **依据**：显式的节点结构描述解决了自动化编码时对 Prefab 内部黑盒的依赖风险，支持在无需打开编辑器的情况下进行精准的 JSON 级预制体修复。

### IX. 性能与内存优化

针对小游戏高频率交互特点进行的限制。

- **逻辑网格管理**：对于具备矩阵结构的游戏（如消除、排序），必须维护一份逻辑上的二维或三维数组（Logic Grid）来管理状态，而非仅依赖物理位置。
- **撤销与状态恢复**：若游戏包含撤销 (Undo)功能，必须使用基于 栈 (Stack) 的状态快照模式。撤销快照应仅包含恢复状态所需的最小数据集，且必须设置容量上限（推荐 10-20 次）以防止内存溢出。
- **依据**：逻辑与表现分离（MVC 思想）是复杂小游戏逻辑不出现紊乱的关键；标准化的快照模式确保了可预测的撤销行为。

### X. 代码自检与质量准入

开发者在提交代码或合并请求前必须进行的自我验证。

- **自检清单**：所有非微型改动都必须基于生成的 `checklist` 完成自检，涵盖：核心业务路径覆盖、边界条件测试、UI 面板重排布校验、内存泄漏风险评估（如未销毁的监听）。
- **编译检测**：在每个任务 (Task) 标记完成前，必须执行全量代码静态检测（Compilation Check），确保工作区无任何编译错误或严重的类型警告。
- **闭环要求**：禁止将带有TODO且无后续追踪计划的代码合并至主分支。
- **依据**：前置质量检查可以显著降低 CI 测试失败率及返工成本。

### XI. 单元测试驱动

针对核心逻辑的自动化保障。

- **强制范围**：所有 `util` 类、核心算法（如排序算法、网格路径查找）、以及关键的数据层逻辑必须编写单元测试。
- **测试时机**：推荐采用测试驱动开发（TDD）或在功能开发完成后立即补全测试用例。单元测试失败时不准进行代码合并。
- **依据**：小游戏逻辑迭代频繁，单元测试是保障回归测试稳定性和重构信心的基石。

### XII. 事件驱动与服务解耦

为了降低系统复杂性，不同模块间的深层交互应优先使用事件通知。

- **事件总线**：全局或模块间的状态变更通知建议使用 `cc.director.emit` 或自定义的 `EventBus` 实例。
- **订阅生命周期**：所有注册的监听器（`on`）必须在对象销毁或不再需要时取消订阅（`off`）。
- **单例模式规范 (Logic Singleton)**：非 Component 类型的逻辑控制类（如 `BusControl`）严禁重复实例化。必须继承自 `assets/ace/logic/Singleton.ts`，并提供 `static get instance()` 访问器。核心依赖项应通过 `init()` 方法在游戏启动阶段注入，而非通过构造函数传递。 (P21)
- **依据**：过度依赖单例模式（Static Instance）会导致模块间高度耦合，难以维护。事件驱动可以实现发送方与接收方的完全隔离；而标准化的 Singleton 继承则保证了 Logic 层访问的唯一性与一致性。

### XIII. 配置驱动与可外部化

每个新增的小游戏必须遵守数据与逻辑分离的原则，提升灵活性及可测试性。

- **配置独立化**：游戏可能的配置项（如数值平衡、关卡布局、资源映射等）必须从核心逻辑类中独立出来，存放在外部 JSON 文件或专用的配置管理类中。
- **动态配置接口**：小游戏必须保留外部替换参数配置的接口或功能。支持在初始化阶段或运行时通过注入方式覆盖默认参数，严禁将关键玩法参数硬编码。
- **依据**：配置解耦能够极大提升游戏的调优效率，且允许自动化工具（或运维系统）在不修改代码的情况下改变游戏行为。

### XIV. 标准化配置模式 (Standardized Configuration Pattern)

所有小游戏必须遵循统一的内存配置管理模式，以确保开发一致性及参数合并的可预测性。

- **接口定义**：必须定义名为 `IGameConfig` 的接口，穷举所有玩法及表现参数。
- **默认值**：必须定义名为 `DEFAULT_GAME_CONFIG` 的静态常量，为所有参数提供基准值。
- **合并逻辑**：在配置刷新（如 `refreshConfig`）时，必须使用展开运算符 (`...`) 将来自外部或服务器的 `Partial<IGameConfig>` 覆盖到默认配置上（例如：`this.config = { ...DEFAULT_GAME_CONFIG, ...this.gamePara }`）。
- **禁止项**：禁止在业务逻辑中直接修改 `DEFAULT_GAME_CONFIG`；禁止在没有定义默认值的情况下直接使用外部下发参数。
- **依据**：标准化的配置模式使得 AI 助手能够快速理解不同游戏的参数逻辑，并极大降低了因缺少某个配置项导致的运行时错误。

### XV. 开发辅助工具规范 (Development Tooling Specification)

为了确保工具链的可维护性及环境一致性，所有开发辅助脚本必须符合特定要求。

- **语言一致性**：所有内部工具、自动化脚本、构建钩子等建议优先使用 Node.js (JavaScript/TypeScript) 编写。**非必要不使用 Python**、Bash、PowerShell (非内置命令) 等其他脚本语言。
- **Agent 环境锁定**：AI 助手在执行逻辑运算、数据处理或 UUID 压缩等任务时，应优先通过 Node.js 代码片段（Pylance 工具链中的 Node 运行时）或工作区现有的工具类实现，避免产生不必要的 Python 依赖。
- **使用授权**：在使用 `prefabBuilder` 等自动化工具修改或重新构建预制体（Prefab）之前，AI 助手**必须先征得用户明确同意**，严禁在未通知的情况下自动执行构建命令。这一流程确保了开发者对资源库（Assets）变动的绝对知情权与控制权。
- **存储与文档**：工具必须存放在 `tools/` 根目录下。每个子项工具必须包含一个 `README.md` 描述其用途、参数及运行步骤，并补全完整的 JSDoc 注释。
- **依据**：统一的技术栈可以降低团队成员之间的协作门槛，并协助避免意外故障。

### XVI. 预制体脚手架与组件绑定 (Prefab Scaffolding & Binding)

在 Cocos 2.3.x 环境下，通过 JSON 直接修复或生成 Prefab 必须遵循自动化准入流程。

- **脚手架生成标准**：
    - 必须根据脚本 JSDoc 中的 `[Prefab 结构说明]` 补全缺失的子节点。
    - 必须为根节点自动挂载对应的脚本组件，其 `__type__` 必须使用 **23 位压缩 UUID**（计算公式：`prefix(5) + base64(rest_hex)`）。
- **组件自动绑定**：
    - 对于脚本中的 `@property`，必须在 JSON 中执行自动绑定。若引用的是其他资源（如 Prefab），必须通过查询其对应 `.meta` 文件的 `uuid` 进行 `__uuid__` 字段关联。
    - **[重要]** `cc.PrefabInfo` 中的 `asset` 字段必须引用 **预制体自身的 UUID**，而非脚本或子节点的 UUID。
- **结构清理**：
    - 严禁在 Prefab JSON 中保留重复的 `__id__` 或失效的脚本引用（如 `__type__: "6614d..."` 应纠正为计算后的正确值）。
- **依据**：标准化的脚手架流程确保了代码驱动预制体的可行性，使得开发者可以通过修改脚本说明快速同步预制体结构，降低编辑器人工操作引入的随机错误风险。

### XVII. 代码先行预制体自动化流 (Code-First Prefab Automation)

在 `speckit.plan` 完成功能规划并定义好脚本 JSDoc 结构后，应进入自动化 Prefab 构建阶段。

- **前置时机**：禁止在最后阶段才手工组装 Prefab。一旦脚本框架及 JSDoc 中的 `[Prefab 结构说明]` 确定，必须立即使用自动化工具（或 AI 助手）生成或同步对应的 `.prefab` 基准文件。
- **业务组装**：生成的 Prefab 应根据规格说明书（spec.md）中定义的业务逻辑，自动完成节点树的初步组装及属性绑定，确保代码编写完成后可直接进行运行调试。
- **依据**：将 Prefab 创建作为开发流的早期环节，可强制保证脚本设计与资源结构的高度对齐，大幅减少因资源缺失或节点路径变更导致的假性 Bug。

### XVIII. 快速原型与 Demo 导向 (Rapid Prototyping & Demo Driven)

本项目的核心目标是利用 AI 助手快速生成游戏 Demo 和原型，以验证核心玩法。

- **速度优先**：在确保核心逻辑正确及符合本宪法基本安全原则的前提下，应优先采用能够快速验证玩法的实现方式。
- **模块重用**：鼓励建立和使用可重用的 UI 组件、通用的游戏控制器和逻辑单例模块，以缩短从构思到可运行 Demo 的时间。
- **依据**：通过极速的开发迭代和原型演示，可以更早地发现设计冲突并验证核心趣味性，适配小游戏快速迭代的市场节奏。

## 附加约束

### 技术栈

- **编辑器**：Cocos Creator 2.3.x (强制限定)。
    - **UUID 规范**：手动编辑或修复 Prefab 时，必须使用 **23 位压缩 UUID**（基于 5位前缀 + 18位 Base64 映射），否则 Class ID 注册将失效。
- **语言**：TypeScript。
- **测试框架**：Cocos Test Runner / Jest。
- **格式化**：Prettier + ESLint (Alloy)。

### 目录合规性

- 所有游戏逻辑代码必须位于 `assets/script/game/`。
- UI 相关脚本必须位于 `assets/script/ui/`。
- Prefab 专用脚本必须位于 `assets/script/prefab/`。
- 跨平台/SDK 逻辑 must be located in `assets/script/platform/`。

## 治理

本宪法高于所有个人偏好及先前的实践。

- **修订**：需要进行版本更新（遵循语义化版本），并提供适用的迁移计划。
- **执行**：CI/CD（ESLint 检查、自动化测试）及 PR 审查是主要的守门人。
- **合规性**：所有任务及方案必须根据这些原则进行验证。
